# تجهيز الإصدارات والتحديثات

## الربط الحالي

مصدر المشروع الحالي يستخدم `KeRoDeveloper2026/KeRo-Smarter-Download`.
التطبيق المثبّت يفحص التحديثات عند التشغيل ثم كل ست ساعات، ويمكن الفحص من قائمة المساعدة.
عنوان بيانات آخر إصدار:

`https://github.com/KeRoDeveloper2026/KeRo-Smarter-Download/releases/latest/download/version.json`

لا يكفي رفع المصدر: يجب بناء المثبّت ونشره مع `version.json` الموقّع.
الإصدار المنشور سابقًا 1.1.0 لا يحتوي على بيانات تحديث موقّعة. النسخ القديمة ذات الرابط القديم أو التحديث المعطّل تحتاج إلى تثبيت النسخة الجديدة يدويًا مرة واحدة.

## إعداد مفتاح التوقيع مرة واحدة

يتحقق التطبيق من Ed25519 وبصمة SHA-256 قبل التثبيت. يجب أن يطابق سر Actions المسمى `UPDATE_SIGNING_KEY` المفتاح العام `UPDATE_PUBLIC_KEY` داخل `crates/engine/src/selfupdate.rs`.
إذا كان السر الصحيح موجودًا بالفعل، لا تغيّره. يتحقق سير البناء من تطابقه قبل المتابعة.

إذا كنت تملك المفتاح الخاص الحالي، ضعه في متغير البيئة `UPDATE_SIGNING_KEY` محليًا وشغّل السكربت دون `--generate`.
إذا لم تملكه، أنشئ هوية توقيع جديدة مرة واحدة بالأوامر التالية من نسخة Git محلية للمشروع. تحتاج Python وGit و[GitHub CLI](https://cli.github.com/) وحساب المالك:

```powershell
git switch main
git pull --ff-only
python -m pip install cryptography
gh auth login
python tools/setup-update-signing.py --generate
git add crates/engine/src/selfupdate.rs
git commit -m "Configure update signing public key"
git push origin main
```

يرسل السكربت المفتاح الخاص مباشرة إلى GitHub Secret دون طباعته أو حفظه في ملفات، ويعدّل المفتاح العام فقط. إذا فشل ضبط السر فلن يعدّل المصدر. لا تشارك المفتاح الخاص في المحادثة أو المستودع.
تغيير هوية التوقيع لاحقًا يستلزم تثبيتًا يدويًا للنسخ التي تثق بالمفتاح السابق؛ لذلك لا تكرر `--generate` لكل إصدار.
صلاحيات إضافة GitHub داخل ChatGPT لا تشمل إدارة Secrets؛ تشغيل هذه الخطوة محليًا يضبط السر بصلاحيات حسابك.

توقيع التحديث منفصل عن شهادة Authenticode لملفات Windows.

## البناء والنشر

1. جهّز التغييرات المراجَعة على `main`، وزِد رقم النسخة في `Cargo.toml` لكل إصدار جديد.
2. شغّل `cargo update --workspace` بعد تغيير رقم النسخة، وراجع فرق `Cargo.lock` واحفظ الملفين معًا. لا تحدّث كل المكتبات لمجرد إصدار نسخة جديدة.
3. انتظر نجاح **Quality checks**: التنسيق، Clippy الصارم، اختبارات المحرك والإضافة، فحص الثغرات والتحقق من مصادر إصلاح Windows 7.
4. أنشئ وسمًا مطابقًا تمامًا للنسخة، مثل `v1.1.4`، وارفعه. مثال توضيحي فقط؛ لا تستخدم نفس الوسم لإصدار آخر:

```sh
git tag -a v1.1.4 -m "KeRo Smarter Download 1.1.4"
git push origin v1.1.4
```

5. يعمل **Build KeRo Smarter Download for Windows** تلقائيًا على الوسم. يتحقق من مطابقته لـCargo.toml ومن وجود commit ضمن تاريخ `main`، ويعيد فحوصات الجودة لنفس commit قبل بناء الحزمة.
6. يجب وجود `UPDATE_SIGNING_KEY` الصحيح للنشر. يُرفق المثبّت و`version.json` الموقّع، وتُنشأ Release notes تلقائية. راجع الملاحظات بعد الإنشاء وأضف شرحًا للمستخدم عند الحاجة؛ التوليد التلقائي لا يغني عن ملخص واضح.
7. لا يستبدل السير إصدارًا موجودًا، ويتحقق مجددًا من عدم تحريك الوسم قبل النشر. رسائل commit التي تتضمن `[release]` لا تنشر إصدارات.

التشغيل اليدوي من **Run workflow** على `main` مخصص لاختبار حزمة Windows x64، ولا ينشر Release. سير الوسم الأساسي يبني حزمة Windows 10/11 x64؛ بناء حزم Windows 7 التجريبية يتم صراحةً من **Additional Windows architectures** بعد وجود إصدار النسخة المناسب. لا يعاد بناء Windows 10/11 x86 ضمن فحوصات الجودة. تبقى ملفات v1.1.3 الحالية وروابطها دون تغيير.

اختبر المثبّت والتنزيل والاستئناف ودمج الوسائط والإضافات واللغات على الأنظمة المستهدفة قبل توسيع التوزيع. نجاح CI على Windows Server لا يثبت التوافق الفعلي مع Windows 7. تتطلب تحديثات المستخدم رقم نسخة أعلى والتوقيع بالمفتاح نفسه.

للبناء المحلي شغّل `BUILD.bat`. وجود `UPDATE_SIGNING_KEY` محليًا يتيح إنتاج بيانات تحديث موقّعة؛ لا تنشر مفاتيحك ضمن المصدر.

## Firefox

الإضافة المرفقة غير موقّعة ومخصصة للتطوير المؤقت. يدعم سير العمل توقيعها باستخدام `AMO_JWT_ISSUER` و`AMO_JWT_SECRET`، أو حزمة موقّعة مجهزة مسبقًا. توقيع Firefox مستقل عن تحديث التطبيق.

## ملف قفل المكتبات

يجب تضمين `Cargo.lock` المراجع في commit الإصدار. بعد تغيير رقم نسخة المشروع في `Cargo.toml`، شغّل `cargo update --workspace` وراجع فرق القفل قبل حفظه؛ لا تستخدم تحديثًا شاملًا لكل المكتبات لمجرد تغيير رقم النسخة. تستخدم أوامر المشروع `--locked`؛ لا تحذف ملف القفل لتجاوز فشل البناء. عند تحديث المكتبات عمدًا، راجع فرق القفل وأعد اختبارات التوافق أولًا. يتضمن القفل مكتبات كل المنصات، ولا يثبّت إصدار Rust نفسه أو الأدوات الخارجية مثل yt-dlp وFFmpeg. راجع [سياسة المكتبات والبناء](DEPENDENCIES.md).

## حماية مفتاح توقيع التحديث

المفتاح الخاص Ed25519 سلطة توقيع تحديثات البرنامج، وهو منفصل عن Cookies وDPAPI وشهادة Authenticode ومفاتيح Mozilla. لم يغيّر هذا التعديل المفتاح العام الحالي أو صيغة التوقيع؛ تظل النسخ المثبّتة تثق بنفس الهوية.

### ضوابط مطبّقة في ملفات البناء

- فحوصات Pull Requests وCI العادية لا تستلم مفتاح التوقيع. البناء اليدوي الأساسي لا يستلمه كذلك، ولا ينشئ بيانات تحديث موقّعة.
- يتم تجميع أداة التوقيع من المصدر المراجع بدون مفتاح. يُمرّر المفتاح عند تشغيل الأداة المجمّعة فقط، ويُزال متغير البيئة بعدها حتى عند فشل الأداة.
- تحذف مرحلة التعبئة المفتاح من بيئتها قبل تشغيل الأدوات المساعدة، فلا ترثه كمتغير بيئة. يبقى مؤقتًا في ذاكرة عملية التعبئة؛ هذا تقليل للتعرض وليس عزلًا أمنيًا من كود خبيث يعمل بنفس صلاحيات runner.
- سير الوسم يتحقق من النسخة ومن صلة commit بتاريخ main، وينتظر نجاح فحوصات الجودة. لا تُستبدل مرفقات إصدار موجود تلقائيًا.
- في البناء المحلي، تُزال قيمة UPDATE_SIGNING_KEY من بيئة PowerShell أثناء البناء والتعبئة وبعد التوقيع. لا تستخدم dot-sourcing لتشغيل سكربت البناء، ولا تطبع المفتاح للتحقق منه. تشغيل tools/package-platform.ps1 مباشرة يتطلب تجهيز target/release/examples/sign_update.exe مسبقًا بدون أسرار.

### إعدادات حساب ومستودع يراجعها المالك

هذه قائمة إعداد وليست ادعاءً بأن إعدادات GitHub الإدارية فُعّلت بواسطة تعديل الملفات:

1. استخدم MFA أو passkey للحساب، وراجع مالكي المستودع وصلاحيات Collaborators وGitHub Apps وPATs. احصر سلطة تعديل workflows ووسوم الإصدارات في جهات موثوقة.
2. احمِ main ووسوم v* بقواعد مناسبة، وراجع تغييرات workflows وملفات الاعتماد قبل النشر. تثبيت Action على SHA لا يغني عن مراجعة SHA الجديد.
3. يُنصح ببيئة GitHub محمية للتوقيع والنشر، مع قصر فروع/وسوم النشر ومراجعة الوصول إلى أسرارها. لا تنقل Secret قبل ربط كل job الموقّع بالبيئة واختبار مسار النشر؛ وإلا سيتعطل النشر. إذا كنت المسؤول الوحيد، لا تمنع المراجعة الذاتية قبل وجود مراجع آخر موثوق.
4. لا تحفظ المفتاح في Git أو المرفقات أو artifact أو سجل CI أو صورة شاشة. راجع السجلات بعد أي تعديل في مسار التوقيع. احفظ نسخة استرداد مشفّرة منفصلة، بصلاحيات محدودة، إذا كانت النسخة الأصلية متاحة لديك؛ GitHub Secrets لا يتيح قراءة المفتاح الحالي لاسترجاعه.
5. لا تبدّل المفتاح دوريًا بصورة عمياء: العميل الحالي يثق بمفتاح عام واحد ولا يطبّق بروتوكولًا لاستبدال جذر الثقة. أي تغيير حقيقي للهوية يحتاج خطة انتقال واختبارًا، وليس مجرد تغيير Secret.

مرجع إعداد البيئات: https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments

### خطة الاستجابة عند الاشتباه بتسرّب المفتاح

1. أوقف التوقيع والنشر فورًا، وعطّل workflows المخوّلة إذا لزم، وألغِ صلاحيات وتوكنات الجهات المشتبه بها. لا تنشر تحديثًا تجريبيًا بالمفتاح المشتبه به.
2. احفظ الأدلة وسجلات التدقيق بطريقة خاصة، وحدد وقت الاختراق والإصدارات والمرفقات المتأثرة. راجع تغييرات main والوسوم وworkflows والأصول المنشورة، ولا تنشر بيانات حساسة أثناء التحقيق.
3. احذف/استبدل Secret المتسرّب وأمّن الحساب والبيئة، لكن تذكّر أن ذلك لا يُبطل التوقيعات التي يمكن إنشاؤها بنسخة المفتاح المسروقة. رفض الثقة بالمفتاح القديم على أجهزة المستخدمين يحتاج تغييرًا في العميل أو قناة ثقة مستقلة.
4. اسحب المرفقات المثبت تلوثها وحدد الإصدارات المتأثرة بدقة، وانشر تنبيهًا واضحًا عبر قنوات موثوقة. لا تحذف كل الإصدارات السليمة أو تغيّر Latest عشوائيًا؛ تجنب توجيه العميل إلى حزمة غير متوافقة أو غير موثوقة.
5. أنشئ هوية توقيع جديدة داخل بيئة نظيفة، وابنِ نسخة استرداد من مصدر مراجع، وراجع Hashes وهوية الناشر إن وُجد توقيع Windows. لا تستخدم توقيع المفتاح المخترق وحده لإثبات شرعية المفتاح الجديد.
6. العميل الحالي لا يدعم إبطال مفتاح التحديث عن بُعد أو انتقال ثقة آليًا. قد يلزم أن يوقف المستخدم التحديث التلقائي ويثبت نسخة استرداد يدويًا من قناة موثوقة تم التحقق منها بشكل مستقل. النسخة ذات المفتاح العام القديم سترفض تحديثًا موقعًا بالمفتاح الجديد وحده؛ هذا سلوك أمني متوقع.
7. اختبر النسخة الجديدة على المنصات المدعومة، ووثّق خطوات الانتقال والتحقق للمستخدمين، ثم استأنف النشر بالمفتاح الجديد بعد احتواء الاختراق. يحتفظ تقرير الحادث بالإصدارات والبصمات والقنوات الموثوقة وخطوات منع التكرار دون تضمين أي مفتاح خاص.

الانتقال التلقائي بين المفاتيح يحتاج تصميمًا منفصلًا لجذر ثقة واسترداد آمن؛ هذه الخطة لا تدّعي إضافة تلك الميزة، ولا تطلب تغيير المفتاح السليم الحالي.

## نشر المثبّتات المعتمدة دون إعادة بنائها

الإصدار v1.1.4 يستخدم `.github/workflows/publish-v1.1.4.yml` لنشر المثبّتات الأربعة التي وافق عليها المالك من تشغيل المعاينة `40953114738`، كما هي تمامًا. يسجّل `.github/releases/v1.1.4.json` بصمات المثبّتات ومعرّفات المرفقات ومصدرها وفحوص الجودة.

- يطابق مسار النشر مدخلات بناء التطبيق مع commit المعاينة؛ يسمح فقط بتغييرات التوثيق وأدوات النشر خارج تلك المدخلات.
- يُجمّع مثال `sign_update` وحده دون أسرار، ولا يُعاد بناء التطبيق أو المثبّت. يُمرّر المفتاح إلى عملية التوقيع المجمّعة فقط، ثم يُحذف متغير البيئة.
- يحفظ `release-v1.1.4-ready` الحمولة الموقعة كاملة قبل النشر. عند تعطل النشر، أعد job `publish` وحده من التشغيل نفسه؛ لا تعد بناء النسخ الناجحة ولا تستبدل مرفقًا مختلف البصمة.
- تُرفع المرفقات إلى Draft، وتُراجع بصماتها جميعًا قبل تحويله إلى إصدار منشور وLatest. المحاولة المتكررة تتجاوز المرفقات الموجودة المطابقة، وترفض أي اختلاف دون `--clobber`.
- يُنشأ الوسم باستخدام `GITHUB_TOKEN` داخل مسار الترقية؛ أحداث push الناتجة عنه لا تشغّل مسار بناء آخر. لا تُعد دفع الوسم يدويًا لبدء بناء مكرر. المرجع: https://docs.github.com/en/actions/concepts/security/github_token
- `PROVENANCE.json` و`SHA256SUMS.txt` يربطان الملفات المنشورة بالمعاينة المعتمدة. بعد النشر تُحدّث روابط README واللغات إلى الإصدار المتاح فعليًا.

المسار مقيد بهذا الإصدار؛ اعتماد إصدار لاحق يحتاج خطة وبصمات ومخرجات اختبارات جديدة. لا تغيّر مفتاح التحديث الحالي من أجل ترقية الملفات.

## مزامنة رقم الإضافة مع البرنامج

بعد تحديث version في Cargo.toml، شغّل `python tools/sync-extension-version.py` ثم راجع ملفات manifest الثلاثة واحفظها في Git. استخدم `python tools/sync-extension-version.py --check` للتحقق دون تعديل. تغليف الإضافات في CI يرفض اختلاف رقم الإضافة عن رقم البرنامج. أرقام Chromium وFirefox وFirefox-Win7 متطابقة.

تم نشر حزم إضافة مستقلة 1.1.4 لتوحيد الرقم مع البرنامج v1.1.4؛ تغيير الترقيم لا يتطلب إعادة بناء المثبّتات الناجحة أو استبدالها. مثبّتات البرنامج المنشورة لا تزال تضم 1.1.1، لذا حدّث الإضافة من الحزمة المستقلة. التحديث التالي للبرنامج سيضم رقم الإضافة المتزامن وقت بنائه. لا يبدّل تغيير الرقم هوية الإضافة أو صلاحياتها ولا يمنح توقيع Mozilla تلقائيًا.
